# 🏗️ সিনারিও-ভিত্তিক সিস্টেম ডিজাইন ইন্টারভিউ প্রবলেম ও উত্তর
### (Scenario-Based System Design Problems & Solutions)
**টার্গেট:** Mid-to-Senior Software Engineers / Full-Stack Developers  
**উদ্দেশ্য:** বাস্তব ব্যবসায়িক চ্যালেঞ্জের মুখে প্রার্থীর আর্কিটেকচারাল চিন্তাভাবনা, ডেটা ইন্টিগ্রিটি ও হাই-লোড সামলানোর ক্ষমতা যাচাই।

## 🎯 সিনারিও ১: ডাবল-বুকিং ছাড়া রিয়েল-টাইম অ্যাপয়েন্টমেন্ট / স্লট বুকিং সিস্টেম
> **বাস্তব প্রেক্ষাপট:** একটি জনপ্রিয় সেলুন বা ডক্টরস ক্লিনিকে প্রতিদিন শত শত কাস্টমার অনলাইনে নির্দিষ্ট টাইম-স্লট (যেমন: বিকাল ৪:০০–৪:৩০) বুক করে। দুই বা ততোধিক কাস্টমার একই মিলিসেকেন্ডে একই চেয়ার বা স্লটে ক্লিক করলে যেন **ডাবল বুকিং (Double Booking)** না হয় এবং বুকিং চলাকালীন ৫ মিনিট স্লটটি অন্য কারো জন্য লক থাকে।

### ⚙️ প্রযুক্তিগত চ্যালেঞ্জ:
1. Race Condition রোধ করা।
2. কাস্টমার পেমেন্ট পেজে গিয়ে যদি উইন্ডো কেটে দেয়, স্লটটি যেন আজীবনের জন্য আটকে না থাকে (TTL / Auto-Release)।
3. সিস্টেম ফাস্ট রাখা।

### 💡 আদর্শ সমাধান ও আর্কিটেকচার:
```
[কাস্টমার স্লট সিলেক্ট করল] ➡️ [Redis Temporary Lock (TTL: 5 Min)]
                                       ⬇️
                              [পেমেন্ট গেটওয়েতে পাঠানো হলো]
                                ↙️                      ↘️
                 [পেমেন্ট সফল: DB-তে বুকড]       [পেমেন্ট ফেইল / টাইমআউট: Redis কি ডিলিট]
```
1. **স্লটের ৪টি স্ট্যাটাস:** `Available`, `Reserved_Temporary`, `Confirmed_Booked`, `Cancelled`।
2. **Redis Distributed Lock / TTL:** কাস্টমার যখন স্লটে ক্লিক করবে, লারাভেল বা ব্যাকএন্ড Redis-এ একটি কী সেট করবে:  
   `SET slot_lock:105:2026-10-15 "user_42" NX EX 300` (NX = যদি অলরেডি লক না থাকে, EX 300 = ৫ মিনিটের মেয়াদ)।
   - অন্য কেউ একই স্লটে ক্লিক করলে সাথে সাথে দেখাবে: *"এই স্লটটি সাময়িকভাবে অন্য কাস্টমার বুক করছেন, অনুগ্রহ করে অপেক্ষা করুন।"*
3. **Pessimistic Lock (`lockForUpdate`):** পেমেন্ট কনফার্মেশনের পর ডাটাবেজে ফাইনাল বুকিং করার সময়:
   ```php
   DB::transaction(function() use ($slotId, $userId) {
       $slot = Slot::where('id', $slotId)->lockForUpdate()->first();
       if ($slot->status !== 'Available') {
           throw new Exception('Slot already taken');
       }
       $slot->update(['status' => 'Confirmed_Booked', 'booked_by' => $userId]);
   });
   ```
4. **অটো-রিলিজ:** যদি ৫ মিনিটের মধ্যে পেমেন্ট না আসে, Redis-এর TTL এক্সপায়ার হয়ে স্লটটি স্বয়ংক্রিয়ভাবে সবার জন্য আবার `Available` হয়ে যাবে।

* 🚩 **রেড ফ্ল্যাগ:** প্রার্থী যদি বলে "MySQL-এ সিলেক্ট করে চেক করব `if ($status == 'available')`"—কনকারেন্ট ট্রাফিকে এটা নিশ্চিত ফেইল করবে।

## 🎯 সিনারিও ২: মাল্টি-টেন্যান্ট SaaS সফটওয়্যার আর্কিটেকচার (Multi-Tenancy)
> **বাস্তব প্রেক্ষাপট:** আপনার ERP বা CRM সিস্টেমে ১০০টি আলাদা কোম্পানি সাবস্ক্রিপশন নিয়ে কাজ করছে (যেমন: `company1.pserp.xyz`, `company2.pserp.xyz`)। কোনো অবস্থাতেই এক কোম্পানির কর্মী যেন অন্য কোম্পানির কোনো ডেটা দেখতে না পারে।

### ⚙️ প্রযুক্তিগত চ্যালেঞ্জ:
1. Data Isolation ও সিকিউরিটি।
2. পারফরম্যান্স ও ব্যাকআপ নেওয়ার সহজ উপায়।

### 💡 আদর্শ সমাধান ও আর্কিটেকচার:
সফটওয়্যার ইঞ্জিনিয়ার হিসেবে প্রার্থীকে **২টি পদ্ধতির সুবিধা-অসুবিধা (Trade-offs)** তুলনা করতে জানতে হবে:

| পদ্ধতি | কীভাবে কাজ করে? | সুবিধা | অসুবিধা |
| :--- | :--- | :--- | :--- |
| **পদ্ধতি ১: Single Database (Shared DB with Tenant ID)** | সব কোম্পানির ডেটা একটি ডাটাবেজেই থাকবে, প্রতিটি টেবিলে `tenant_id` বা `company_id` কলাম থাকবে। | সার্ভার খরচ কম, মাইগ্রেশন চালানো সহজ। | কোডে ভুল হলে এক কোম্পানির ডেটা অন্য কোম্পানিতে লিক হওয়ার ঝুঁকি থাকে। |
| **পদ্ধতি ২: Multi-Database (Database per Tenant)** | প্রতিটি কোম্পানির জন্য সম্পূর্ণ আলাদা MySQL ডাটাবেজ। | ১০০% সুরক্ষিত, কোনো ডেটা লিকের ভয় নেই। ব্যাকআপ আলাদা নেওয়া যায়। | শত শত ডাটাবেজ মেইনটেইন করা এবং মাইগ্রেশন চালানো জটিল। |

#### লারাভেলে পদ্ধতি ১ (সবচেয়ে বেশি ব্যবহৃত) সুরক্ষিত রাখার কৌশল:
* **Tenant Middleware:** সাবডোমেইন (`request()->getHost()`) দেখে কারেন্ট কোম্পানি চিহ্নিত করবে।
* **Global Scope:** প্রতিটি মডেলে একটি গ্লোবাল স্কোপ থাকবে:
  ```php
  static::addGlobalScope('tenant', function (Builder $builder) {
      $builder->where('tenant_id', session('current_tenant_id'));
  });
  ```
  এর ফলে ডেভেলপার ভুলে `where('tenant_id')` লিখতে ভুলে গেলেও লারাভেল স্বয়ংক্রিয়ভাবে অন্য কোম্পানির ডেটা হাইড রাখবে।

## 🎯 সিনারিও ৩: পেমেন্ট ফেইল ও নেটওয়ার্ক ড্রপ অটো-রিকনসিলিয়েশন (Payment Reconciliation)
> **বাস্তব প্রেক্ষাপট:** একজন ক্লায়েন্ট বিকাশে ৫,০০০ টাকা পেমেন্ট করেছে। ব্যাংকে টাকা কেটে নিয়েছে, কিন্তু কাস্টমারের মোবাইল নেটওয়ার্ক ড্রপ করায় সে আর ব্যাক করতে পারল না এবং আপনার সার্ভারেও তাৎক্ষণিক কলব্যাক আসেনি। কাস্টমার ব্যালেন্স কীভাবে সেভ করবেন?

### ⚙️ প্রযুক্তিগত চ্যালেঞ্জ:
1. কাস্টমারের টাকা কেটেছে কিন্তু অর্ডারে দেখাচ্ছে "Pending/Unpaid"।
2. সাপোর্ট টিমের ম্যানুয়াল কল ছাড়াই অটোমেটিক ব্যালেন্স আপডেট হওয়া।

### 💡 আদর্শ সমাধান ও আর্কিটেকচার:
```
[পেমেন্ট ইনিশিয়েট: স্ট্যাটাস PENDING]
                ⬇️
[প্রতি ৫ মিনিটে Scheduled Cron Job চলবে]
                ⬇️
[বিকাশ/গেটওয়ের Query API-তে চেক করবে: টাকা কি সত্যি কেটেছে?]
         ↙️                                      ↘️
 [হ্যাঁ: Order PAID + SMS পাঠানো]       [না: ২৪ ঘণ্টা পর EXPIRED মার্ক করা]
```

1. **Payment Intent তৈরি:** পেমেন্ট শুরু হওয়ার সাথে সাথেই ডাটাবেজে `payments` টেবিলে একটি ট্রানজ্যাকশন আইডি ও স্ট্যাটাস `Initiated / Pending` হিসেবে রেকর্ড করা।
2. **Reconciliation Cron Job (সবচেয়ে গুরুত্বপূর্ণ):**  
   লারাভেলে একটি শিডিউলার কমান্ড থাকবে (`php artisan payments:reconcile`), যা প্রতি ৫ বা ১০ মিনিট পর পর চলবে:
   ```php
   $pendingPayments = Payment::where('status', 'Pending')
       ->where('created_at', '<', now()->subMinutes(5))
       ->get();
   
   foreach ($pendingPayments as $payment) {
       // গেটওয়ের অফিসিয়াল স্ট্যাটাস চেক API কল করা
       $gatewayResponse = Http::get("https://payment-gateway/verify/{$payment->trx_id}");
       
       if ($gatewayResponse['transaction_status'] === 'Completed') {
           DB::transaction(function() use ($payment) {
               $payment->update(['status' => 'Success']);
               $payment->invoice->update(['status' => 'Paid']);
           });
       }
   }
   ```
3. **Idempotency:** গেটওয়ে যদি পরে আবার Webhook পাঠায়, সিস্টেম দেখবে স্ট্যাটাস অলরেডি `Success` করা আছে, তাই ডাবল ক্রেডিট বা ডাবল ইনভয়েস জেনারেট করবে না।

## 🎯 সিনারিও ৪: হাই-ভলিউম বাল্ক নোটিফিকেশন ইঞ্জিন (Bulk Notification Engine)
> **বাস্তব প্রেক্ষাপট:** ঈদের অফারে আপনার CRM থেকে ১,০০,০০০ কাস্টমারকে একযোগে SMS ও ইমেইল পাঠাতে হবে। কিন্তু SMS গেটওয়ের সীমাবদ্ধতা হলো—তারা প্রতি সেকেন্ডে সর্বোচ্চ ৫০টি SMS গ্রহণ করতে পারে। সার্ভার ডাউন না করে এবং গেটওয়ে ব্লক না খেয়ে এটি কীভাবে পাঠাবেন?

### ⚙️ প্রযুক্তিগত চ্যালেঞ্জ:
1. ১০ লাখ রেকর্ডে মেমোরি লিমিট (Out of Memory) না হওয়া।
2. গেটওয়ের রেট লিমিট (৫০ রিকোয়েস্ট/সেকেন্ড) রক্ষা করা।

### 💡 আদর্শ সমাধান ও আর্কিটেকচার:
1. **Chunking & Cursor:** পুরো ১ লাখ ইউজার একবারে অ্যারেতে লোড না করে:
   ```php
   User::chunkById(1000, function ($users) {
       foreach ($users as $user) {
           SendCampaignNotificationJob::dispatch($user)->onQueue('campaigns');
       }
   });
   ```
2. **Queue Rate Limiter (লারাভেল রেডিমেড সলিউশন):**  
   জব ক্লাসের ভেতর লারাভেলের `Redis::throttle` ব্যবহার করা:
   ```php
   Redis::throttle('sms-gateway')
       ->allow(50)->every(1) // প্রতি ১ সেকেন্ডে ৫০টি
       ->then(function () {
           // SMS গেটওয়েতে রিকোয়েস্ট পাঠানো
       }, function () {
           // লিমিট পার হলে জবটি পুনরায় কিউতে রিলিজ করে দেওয়া
           return $this->release(2);
       });
   ```
3. **Dead Letter Queue (DLQ):** যে নম্বরগুলো ভুল বা বন্ধ থাকার কারণে ৩ বার ফেইল করবে, সেগুলো একটি ব্যর্থ তালিকায় আলাদা সেভ হবে যেন ক্যাম্পেইন আটকে না থাকে।

## 🎯 সিনারিও ৫: অফলাইন POS ➡️ অনলাইন ক্লাউড সিঙ্ক (Offline-First Sync)
> **বাস্তব প্রেক্ষাপট:** রিটেল শপে হঠাৎ করে ৩ ঘণ্টা ইন্টারনেট চলে গেল। দোকানদার কিন্তু সেল বন্ধ রাখতে পারবে না, সে অফলাইনেই ক্যাশ মেমো ও বিক্রি কাটবে। ৩ ঘণ্টা পর ইন্টারনেট ফিরে এলে সেই ২০০টি অফলাইন সেল কীভাবে ক্লাউডের সেন্ট্রাল সার্ভারে সিঙ্ক হবে—যাতে সেন্ট্রাল ইনভেন্টরির স্টক এলোমেলো না হয়?

### ⚙️ প্রযুক্তিগত চ্যালেঞ্জ:
1. ইন্টারনেট ছাড়াও সেল করা।
2. অফলাইন ডেটা সেন্ট্রাল সার্ভারে মার্জ করার সময় আইডি কনফ্লিক্ট না হওয়া।

### 💡 আদর্শ সমাধান ও আর্কিটেকচার:
1. **Client-Side Storage (IndexedDB):** ব্রাউজার বা লোকাল অ্যাপে সব সেল ও প্রোডাক্টের ডেটা `IndexedDB`-তে জমা রাখা।
2. **UUID (Universally Unique Identifier):** ডাটাবেজের আইডি হিসেবে অটো-ইনক্রিমেন্ট (`1, 2, 3`) ব্যবহার না করে **UUID** ব্যবহার করা। কারণ অফলাইন থাকা অবস্থায় দুটি ভিন্ন ব্রাঞ্চে একই সাথে আইডি `101` তৈরি হতে পারে, কিন্তু UUID ইউনিক থাকবে।
3. **Event Queue & Sync Agent:**
   - ব্রাউজারে `navigator.onLine` ইভেন্ট লিসেন করা।
   - ইন্টারনেট ফিরে আসার সাথে সাথে ব্যাকগ্রাউন্ডে একটি ব্যাচ রিকোয়েস্ট পাঠানো: `POST /api/pos/sync-batch`।
4. **Idempotent Batch Upsert:** সার্ভার প্রতিটি অর্ডারের UUID মিলিয়ে দেখবে আগে সেভ হয়েছে কিনা; না থাকলে ইনসার্ট করবে এবং স্টক হ্রাস (`decrement`) করবে।
